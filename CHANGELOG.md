# Changelog

## Unreleased
- **Undo and redo of a namespace history** (docs/design/state-definitions-and-instances.md, instances).
  `AuthorityOptions.history` keeps that many client changes with what their paths held before; the new client
  messages `undo` and `redo` (wire codes 13 and 14), `SyncClient.undo()`/`redo()` and `Authority.undo()`/`redo()`/
  `history()` step it back and forward as server writes, so no server logic runs. A new change clears what was
  undone; ephemeral and secret changes are never kept; the history is saved with the namespace. With `access`, only a
  session that may write `# Changelog

 may undo. Tests: `src/authority/History.test.ts`, `src/Client.meta.test.ts`,
  `src/Wire.test.ts`.
- **Local and secret paths** (docs/design/state-definitions-and-instances.md, metadata). `SyncClientOptions.local`
  (a node's `@local`): a change at or below one is never sent; it is kept in the local store's new `local` part and
  laid over the confirmed state and outbox, so it survives a reload on that device. `SyncClientOptions.secret` and
  `AuthorityOptions.secret` (a node's `@secret`): the client sends such a change only while online, drops it while
  offline and never writes it to the local store or the confirmed state; the authority runs access and server logic
  on it, hands it to the `onApplied` handlers, and never applies, logs, pushes, saves or keeps it as a request.
  `SyncClient.setPaths` replaces both lists for a host that learns them from a document. Breaking: the ack result
  `passed` (wire index 4) answers a secret change, and `WriteOutcome` gains it. Tests: `src/Client.meta.test.ts`,
  `src/authority/Secret.test.ts`.
- **`encodeCbor` leaves out undefined members when asked, and writes as deep as it is told** (docs/design/
  statenet-wire-format.md, W3). `CborEncodeOptions` adds `omitUndefined` and `maxDepth`; statenet's mesh protocol 5
  uses both. Fix: the sync wire writes to the depth it reads (`maxDepth` + 4), so a change whose value is at the
  sync depth limit no longer throws when sent. Tests: `src/Cbor.test.ts` ("should leave out a member that is undefined
  only when asked to…"), `src/Wire.test.ts` ("should write and read a change whose value is as deep as the limits
  allow").
- **Sync protocol 4: binary after hello** (docs/design/statenet-wire-format.md, W2). Breaking: `PROTOCOL_VERSION` is 4
  and `PROTOCOL_VERSIONS` `[4]`; a hello of 1 to 3 is `invalid-message`. `createSyncWire(limits?)` (`src/Wire.ts`) is
  one connection's side: `hello` and `error` stay JSON text, every other message is a CBOR array `[code, …fields]`
  with no field names, ops, results, statuses and codes as indexes into their closed lists, paths numbered per side of
  the connection the first time they go (`[n, path]`, then `n`; text past `MAX_WIRE_PATHS`, 4,096), and uuid ids as 16
  bytes. A decoded message passes the same checks as a parsed one (`validateMessage`, new). Breaking: `SyncTransport`,
  `TransportConnection`, `AuthorityConnection` and `AuthoritySession` carry `string | Uint8Array`; the client and each
  authority session read and write through a wire. Breaking: every session gets `durable`, `requests` and ephemeral
  changes, as protocol 3 did; `Authority.submit` lost `protocol`, and the welcome report no longer names one.
  `wireTypeOf(data)` names a binary message's type from its first two bytes, for relays. On the session of
  `node scripts/wire-size.ts` (best of 7 runs on the tower): welcome JSON 105,717 bytes, protocol 4 88,893 (84%); the
  1,000 changes messages 209,532 against 88,831 (42%); writing all of them 1.0 ms as JSON text and 3.1 ms through a wire,
  reading 1.1 ms with `JSON.parse` alone against 5.8 ms through a wire with every message checked. Tests:
  `src/Wire.test.ts` (every message type both ways, path numbers and the table's end, uuid bytes, the welcome's order,
  text and binary refusals, a protocol 3 hello refused as `invalid-message`, `wireTypeOf`), and the authority, client
  and request tests over the wire (`src/__fixtures__/Wired.ts`).
- **A CBOR codec for the binary wire** (docs/design/statenet-wire-format.md, W1). `encodeCbor` and `decodeCbor`
  (`src/Cbor.ts`, no dependency, browser-safe) carry JSON's values in a subset of CBOR, and byte strings with
  `{ bytes: true }`; decoding refuses anything JSON could not carry and input past `CborLimits` (`DEFAULT_CBOR_LIMITS`)
  before allocating for it, with a `CborError` of code `too-large`, `too-deep`, `malformed` or `unsupported`. Nothing
  sends it yet: sync protocol 4 (W2) does. A session of a welcome of 300 orders and 1,000 one-change `changes` messages (`node scripts/wire-size.ts`, best of 7 runs on the tower): JSON 105,717 and 209,532 bytes, CBOR 88,939 and 173,158 (84% and 83%); encoding 1.0 ms as JSON text (UTF-8 bytes included) and 2.3 ms as CBOR, decoding 1.1 ms and 3.4 ms. Most of the saving is meant to come from W2's arrays, path
  numbers and byte ids. Tests: `src/Cbor.test.ts` (the RFC 8949 examples, refusals, limits, and 2,000 generated values
  decoded as `JSON.parse(JSON.stringify(value))` would).
- **A session can follow requests only: `hello.requests`** (docs/design/statenet-requests.md, follow-ups). A protocol 3 `hello` with `requests: true` is welcomed with its requests and no state (`changes: []`) and then gets `requested` and `decided` but no `changes` or `durable`; `requests` with another protocol is `invalid-message`. A relay that serves state from its cache opens one to the owner for a browser's requests. Test: `src/authority/Requests.test.ts` ("should welcome a session that asked for requests only with its requests, and send it no changes or watermark").
- **An owner node's plain host names an authority by its address with `/` as `.`** (`alice.notes.user`), as every client of the address says hello, so a session tunnelled to it is not refused as `wrong-namespace`. Storage is by address, so nothing stored moves. Tests: statenet `src/mesh/groups.test.ts`, `ownerMesh.test.ts`, `clientServer.test.ts`.
- **A request lives as long as its grant's entry says, not its token** (docs/design/statenet-requests.md, R3c). `GrantClaims` gains `requestMs` (a request's life, at most `MAX_REQUEST_MS`, 30 days) and `lasts` (when the entry ends; the token's expiry when absent). `verifyGrant` and `checkAccess` give the smallest of each over the chain (`AccessAllowed.lasts`, `requestMs`; the owner's `lasts` is infinite), a token is refused once `lasts` passes, and the authority ends a request at `min(at + (requestMs ?? lifeMs), lasts)`. Before, a request made with a short-lived token ended with the token. Test: `src/authority/Requests.test.ts` ("should keep a request past its token's expiry for the grant's requestMs, within the entry's lasts").
- **Requests that wait for the owner** (docs/design/statenet-requests.md, R1). Breaking: sync protocol 3 (`PROTOCOL_VERSION`; an authority speaks 1 to 3). With `AuthorityOptions.access`, a change from a protocol 3 session that may `request` its path and not `write` it is kept as a pending request (`StoredRequest`, its id the change's) and acked `requested`; the requester and everyone who may decide it (the owner, or someone who may read and write the path) get `requested { request }` (`SyncRequest`) and, when it ends, `decided { id, status, decidedAt, code?, note? }`; `welcome.requests` lists them again. `approve`, `reject` (with a note) and `withdraw` decide one; one not made is an `error` (`REQUEST_ERROR_CODES`). Approval runs the owner's change handlers with `stale` from the request's base and `ChangeContext.request`; a refusal ends it `rejected` with `logic`. `AuthorityOptions.requests` (`RequestOptions`): 7 days to live, never past the grant, decided ones kept 30 days, 50 per requester and 1000 per namespace (`unsaved` past them), checked every minute, at each hello and decision; a revoked entry ends a request `revoked`. A protocol 1 or 2 session gets `access` as before. `GrantRight` gains `request`. `Authority.submit` answers a change at once, and `OwnerNode` orders through it with the writer's access: `write(address, change, via, access)`, `NodePeer.write` takes `access`, a handoff's `queued` writes keep it (`QueuedWrite`), `OwnerNodeOptions.access` has plain authorities check it, and `WriteOutcome` gains `requested`. The sync client drops a requested change from its outbox and keeps its requests: `onRequests`, `requests()`, `approve`, `reject`, `withdraw`. Tests: `src/authority/Requests.test.ts`, statenet's `src/mesh/groups.test.ts` ("requests across groups").
- **An `EpochStorage` writes nothing for a save that landed already under its epoch** (docs/design/statenet-network.md, S8). One owner's save of a serial is always the same, so such a save is one sent again: after an aggregate restarted, or over another relay. It is answered as saved, writes nothing and never takes the state back. `StoredNamespace.serial` counts every change to what is saved, a `$.server` write and a request too, which take no revision; `isResave` compares the revision, then the serial (`serialOf`: the revision when there is none). `createMemoryEpochStorage` keeps the rule; the interface says it. Tests: `src/authority/Requests.test.ts` ("should write a save that takes no revision under the same epoch, and skip one sent again"), statenet's `src/mesh/aggregate.test.ts`.
- **Grants name an owner and a pattern; relays cut what a reader gets** (docs/design/statenet-permissions.md, S14a). Breaking: `GrantClaims` has `entry` (the permission entry it was made from), `owner` and `pattern` in place of `id`, `address` and `prefix`; a passed-on grant must have the same owner and a pattern its parent's contains. `addressPath` places a namespace's path in its owner's tree, `patternReach` and `grantPattern` read a pattern, and `checkAccess` answers `cut` for a read above the pattern's matches, which a relay applies to that listener's snapshot and changes (`cutTo`, `src/authority/Cut.ts`). Breaking: revocations name the entry (`Relay.revoke(entry, expires)`, `RelayListener.revoked(entry, expires)`). `addressCovers`, `isWithinPrefix` and `grantAllows` are gone; `isWithinPattern` and `touchesPattern` are gone, and the authority's handlers and ephemeral paths use `@punyts/state`'s matcher. Tests: `src/authority/Grants.test.ts` ("should give a reader whose grant reaches below its prefix only what the pattern matches, and refuse such a write", "should place a namespace's path in its owner's tree, and say how far a pattern reaches there").
- **A rejected ack says what kind of refusal it is.** `AckMessage.code` is one of `REJECTION_CODES` (`unsaved`, `access`, `invalid`, `logic`, `unavailable`; `RejectionCode`, `isRejectionCode`), so a client can tell a person why without showing the reason, which server logic may fill with values. The authority sends `unsaved` past `maxUnsaved`, `access` for a grant that does not cover the path, `logic` for a server logic refusal and `invalid` for a server-only path or a missing parent; `WriteOutcome` carries the code of a forwarded write, and an owner node that stopped, moved or closed answers `unavailable`. `parseMessage` refuses a code outside the list. `SyncRejection.code` passes it to `onRejected`. Tests: `src/Validate.test.ts` ("should take a rejection code from the closed list, and refuse another"), `Authority.test.ts`, `Grants.test.ts`, `Ownership.test.ts`, `ServerLogic.test.ts`.
- **A limit of unsaved changes.** `AuthorityOptions.maxUnsaved` (10000 by default) bounds the changes an authority holds while its saves do not land, as a node's do while its link to the aggregate is down. Past it a client change is acked `rejected` and `write` and `writeAll` throw (a batch whole), until a save lands; ephemeral changes still pass. A refusal tries a failed save again, since a refused change starts no save. The authority reports when it starts and stops refusing, with the count. Tests: `Authority.test.ts` (the limit of unsaved changes).
- **Reporting by area, never a value.** Breaking: the `state-sync` category is replaced by `state-sync.client` (start, connect, hello, welcome with snapshot or change count, changes queued, sent and applied by path and revision, acks, revision gaps, reconnects with their delay, revoke, stop), `state-sync.capture` (each captured batch by op and path, with the writes folded), `state-sync.authority` (load and save with their duration in ms, connects and leaves, welcomes, each change applied, adjusted or rejected with the kind of refusal, server writes, close), `state-sync.relay` (upstream subscriptions, welcomes, gaps, epochs, listeners joining, leases and grants ending, changes passed on) and `state-sync.ownership` (taking, claiming, handing off, losing and releasing a namespace, forwarded writes). Per-change reports are guarded with `isReported`. Fix: failures report an error's name, not its message (a storage or handler error may hold values), a client's error by its code only, and a handler's rejection by its kind, not its reason. Tests: `src/Reporting.test.ts`.
- **`FencedError` says what it refused.** It carries `address`, `epoch` (of the refused save) and `current` (the newest epoch the namespace was saved under), so statenet's aggregate can send a fence across the mesh and the node can throw it again.
- **Owner nodes with a host of their own.** `OwnerNode` takes a `host` (`NamespaceHost`): an app server gives its own authorities (with its logic and storage, fencing its saves by the epoch it is given), and may restart them between writes; plain authorities over `storage` stay the default. `place(address)` says where a namespace is ordered (here, taking it when nobody holds it, or at its owner), `owns` whether it is here; `authorityOf` and `stop` are now async. The nodes an owner reaches are `NodePeer`s (`write`, `claim`, `handoff`), so a peer can be another process over the mesh. `Authority.onClose`; `createAuthorityUpstream` never serves `$.server` and closes its listeners when the authority closes. Tests: `Ownership.test.ts`, `Relay.test.ts`.
- **Fix: a relay caches a whole namespace.** A subscription to `# Changelog

 cached nothing, so its snapshots were empty; a change of the whole namespace now replaces the cache. Test: `Relay.test.ts`.
- **Owner nodes and moving ownership.** `OwnerNode` holds the authority of each namespace it owns and passes other writes to the owner; `claim` and `handoff` move a namespace without two writers (the owner stops ordering, waits until it is durable, and hands over its revision, epoch and the writes that came meanwhile), and a namespace whose owner's lease ran out is taken over on the next write. `OwnershipStore` (compare-and-swap on the epoch) and `EpochStorage` (a save from an older epoch is refused with `FencedError`) are ports, with memory versions. `ClaimPolicy` moves ownership only to a node that sends most of the writes, with a cooldown. Relays refuse batches from an older epoch and start over from a snapshot under a newer one. Tests: `Ownership.test.ts`.
- **Grants.** `signGrant`, `verifyGrant` and `checkAccess`: Ed25519-signed read and write grants for an address and a path prefix, a root signed by the owner of the address and grants passed on, each no wider than the one before (`addressCovers`, `isWithinPrefix`), retired keys verifying only what they signed before, and a `RevocationList`. A relay with `grants` checks every subscription's read on subscribe and each renewal, `revoke` closes the listeners whose read rests on a grant and passes the revocation down; `node` and `trustedNodes` let relays trust the relays below them. An authority with `access` checks every client change against its connection's grant (`connect(connection, access)`). Tests: `Grants.test.ts`.
- **Relays.** `createRelay(upstream, options)` serves subscriptions to an address and path prefix: one upstream subscription per address and prefix however many listeners ask, a cache of the prefix with its recent changes, catch-up from the cache (the changes since a listener's revision, or a snapshot), leases (`renew`, `sweep`, `leaseMs`), and a new upstream subscription from its own revision when a batch skips one. `createAuthorityUpstream(resolve)` serves an owner's authorities, projecting each change onto the prefix (`projectChange`). `Authority` has `onChanges` (every committed change) and `changesSince`. Tests: `Relay.test.ts`.
- **Protocol 2: the durable watermark and ephemeral paths.** A client sends `protocol: 2`; an authority speaks 1 and 2. After each save lands the authority sends protocol 2 clients `durable { revision }` (and puts `durable` in `welcome`): every change up to it is stored. `Authority` has `durable()`, `whenDurable(revision?)` and `onDurable`. `AuthorityOptions.ephemeral` lists paths (`*` for one segment) whose changes are applied and pushed marked `ephemeral: true` (to protocol 2 clients) but never saved, never logged in storage and never hold up the watermark. The client reports `pending` (its changes applied but not durable yet, counted only once the authority sends a watermark), has `durable()`, and calls `onDurable(revision, committedIds)`. Tests: `Authority.test.ts` (durability, a client of an authority with a watermark).
- **Works on a page served over plain HTTP on a network address.** `crypto.randomUUID` exists only in a secure context (HTTPS or localhost), so the sync client and capture threw there. Their default ids now come from `randomId()` (exported), which falls back to a version 4 UUID from `crypto.getRandomValues`.
- **Revoked access.** The error code `revoked` (`REVOKED_CODE`) tells a client it may no longer have the namespace. The sync client then stops for good (no reconnect, no save, `start` does nothing), deletes every part of the namespace from its local store (the confirmed state, the outbox and the host's document) and calls `onRevoked(message)`. A client that was offline is told on its next `hello`. `forgetNamespace(store, namespace)` and `LOCAL_PARTS` are exported. For Magnetic's revocable share links.

## 0.8.0
- **Server logic after a change, batched writes and reads.** `authority.onApplied(handler)` runs server logic after a client change is committed and acknowledged, with the change as applied and the client id. `authority.writeAll(writes)` applies server writes in order and pushes those outside `$.server` in one `changes` message, checking every path first. `authority.get(path)` returns a copy of one value. `captureChanges` takes `origins`, write origins captured besides untagged writes (the writes of local logic).
- Docs: the README describes the three modes (Standalone, Persisted, Full) and has security notes (AMM-1822).

## 0.7.0
- **Sparse states.** `applyChange` creates missing parents as empty objects for a set, replace or merge (a merge with nothing to merge into sets), and a delete below a missing parent does nothing. `createAuthority({ createParents: true })` accepts client changes and server writes below a missing parent instead of rejecting them, for states that hold only what a user changed, such as the articulation of `$.app` (AMM-1819).

## 0.6.0
- **`$.server` encryption at rest.** `createAuthority({ serverKey })` saves each direct child of `$.server` encrypted with AES-256-GCM, a fresh nonce and the namespace and name as additional data, and decrypts it on load; a wrong key or tampered data fails with a clear error. Without a key the authority keeps no `$.server`: a server write there throws and a state holding one is refused. `encryptServerBranch` and `decryptServerBranch` are exported. The authority now needs Node (`node:crypto`) (AMM-1816).

## 0.5.0
- **Server logic.** `authority.onChange(pattern, handler)` registers change handlers for wildcard paths that apply, adjust or reject a client change, with the stale flag and the changes since its base; `adjusted` acks carry the value. `authority.write` makes server writes at the next revision, pushed to every client; writes under `$.server` are kept and saved without a revision and never leave the authority. `authority.onEmit` hands client emits to the app server, and `authority.emit` sends one to every client (AMM-1815).

## 0.4.0
- **Authority.** `@punyts/state-sync/authority`: `createAuthority` owns a namespace's order of changes. It answers `hello` with the logged changes or a snapshot, applies each change at the next revision in arrival order, acks it, pushes it to the other connections, applies a repeated change id once, rejects changes under `$.server` or a missing parent, and saves the state, revision, log and applied ids through the `NamespaceStorage` port (`createMemoryNamespaceStorage` for tests). Connections come in through `authority.connect({ send, close })` (AMM-1814).

## 0.3.0
- **Local store and Standalone mode.** The `LocalStore` port with `createWebLocalStore` (over `localStorage`) and `createMemoryLocalStore`. With `localStore` the sync client mounts the saved confirmed state, revision and outbox on start and saves them as they change, coalesced to a microtask; a failed save (a quota error) is reported and sets `saveFailed` in the status while the client keeps running in memory. A client with no `transport` is `standalone`: changes are confirmed at once and kept in the local store. Chromium tests (`npm run test:browser`); the library moves to Vitest 4 (AMM-1813).

## 0.2.0
- **Sync client.** `createSyncClient` keeps the confirmed state and revision and an ordered outbox, shows the confirmed state with the outbox on top through a `StoreBridge`, folds waiting changes, sends `hello` and the outbox on `welcome`, handles `applied`, `adjusted` and `rejected` acks (`onRejected`), catches up again on a revision gap, and reconnects with backoff through a `SyncTransport`, reporting `connecting`, `online` or `offline` and the changes waiting (`onStatus`). `createStoreBridge` is the bridge to a store in the same page, and `applyChange` applies a change with the store's own methods (AMM-1812).

## 0.1.0
- **Changes, messages and capture.** The change and revised change, the sync protocol messages (`hello`, `welcome`, `changes`, `change`, `ack`, `emit`, `error`) with `parseMessage`, which refuses unknown types and keys, wrong shapes, paths that are not sync paths, values that are not JSON and messages past the `SyncLimits`; `isSyncPath`; `captureChanges`, which turns a store's own writes into changes batched to a microtask and folded; and `syncSnapshot` (AMM-1811).
